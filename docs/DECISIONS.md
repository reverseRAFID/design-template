# Decisions

Design choices not covered by the other docs, plus the results of the brand-extraction tasks.
Newest section last. Each entry: what, why, and what would change it.

---

## D1 — Brand orange extracted from the live site (Task 0.1)

**Source:** `https://bracu-mongoltori.com/_next/static/chunks/3u89u9637gr6t.css`

The site ships two themes. The relevant one for us is the dark theme, which is the site's
default presentation and the one our app UI mirrors:

| Token | Light theme (`:root`) | Dark theme (`.dark`) |
|---|---|---|
| `--primary` | `#f05a00` | **`#ff6b1a`** |
| `--primary-hover` | `#d44f00` | **`#ff7d33`** |
| `--primary-active` | `#b34200` | **`#e55a00`** |

**Decision:** `--mt-orange: #FF6B1A`, `--mt-orange-hot: #FF7D33`, `--mt-orange-deep: #E55A00` —
taken verbatim from the dark theme rather than derived by lightness maths, so our accent, hover
and pressed states are pixel-identical to the website's.

The doc fallback `#FF6A1A` was one step off in green; it is now retired.

Incidentally the site's dark background is `#0a0a0a`, which already matches `--mt-bg`.

**Would change it if:** the team rebrands, or decides exports should use the light-theme orange
`#f05a00` for better contrast on cream-toned photos. Worth a look during Phase 4 visual QA.

## D2 — Mongol-Tori logo variants (Task 0.2)

`https://bracu-mongoltori.com/logo-dark.svg` (200) and `/logo.svg` (200) are the same artwork in
two colourways. `/logo-light.svg` does **not** exist (404).

- `logo-dark.svg` — body artwork in `#fff`, accents `#faae42` gold and `#ef4138` red.
  This is the artwork *for* dark backgrounds, so it becomes **`mongoltori-light.svg`**.
- `logo.svg` — body artwork in `#010101`, same gold and red accents.
  Artwork *for* light backgrounds, so it becomes **`mongoltori-dark.svg`**.

Both are clean SVGs with a `viewBox` and no external fonts.

**Two edits applied on import:**

1. `#fff` → `#F4F3EE` in the light variant. Non-negotiable rule 1 forbids pure white, and the
   Design System tone table describes this variant as "cream artwork". The gold and red accents
   are untouched — they are part of the mark.
2. The `.cls-N` class names inside each file are namespaced (`mtl-1`, `mtd-1`, …). The source
   files all use the same generic names; scoping them means two brand SVGs can never collide if
   they ever end up inlined in one document.

**Would change it if:** the team supplies official master artwork. Drop it in at the same paths.

## D3 — BRACU: official artwork on light, derived mono on dark

`https://bracu-mongoltori.com/bracu-logo.svg` is the full-colour institutional mark:
`#2a5caa` blue, `#a7a9ac` grey, `#231f20` near-black.

The Design System requires a light-on-dark / dark-on-light **mono** pair. No mono master was
available, so `bracu-light.svg` and `bracu-dark.svg` are generated by flattening every fill in the
official artwork to `--mt-cream` and `--mt-ink` respectively.

**This is a derivation, not an approved asset.** Flattening a multi-colour institutional logo to a
single tone is normally something a university's brand office signs off on.

**Action for the team:** confirm with BRACU comms, or supply the official single-colour versions.
Until then these are geometrically correct and on-brand, and are the closest available thing.

## D4 — Sponsor logos remain placeholders

The live site loads its sponsor marquee client-side; the SSR HTML contains only empty sized
boxes, and the logo files are not at any guessable path (`/sponsors/*`, `/logos/*`, `/brand/*`
all 404). No sponsor artwork could be extracted.

Two things were recovered and are worth keeping:

- **Ordering.** The site's marquee runs BRACU, CompleTech, MSI, My Actuator, SATEL, SBG Systems,
  Turkish Airlines, Altium, Ansys, Cytron. The manifest's tier guesses are left as the docs had
  them, but this is real evidence about relative prominence when the team confirms tiers.
- **Destination URLs**, stored as an optional `url` field per sponsor. Unused by the renderer;
  useful when someone needs to go find the real logo.

**Decision:** ship **named** placeholders — `sponsors/<slug>-light.svg` and `-dark.svg`, each a
dashed pill containing the sponsor's name — instead of sixteen identical "LOGO" pills. The strip
is then legible enough to QA wrapping, shrinking and tier-dropping against realistic name widths.

The generic `placeholder-light.svg` / `placeholder-dark.svg` pair still exists and is still the
loader's fallback for a genuinely missing file, exactly as the Architecture describes.

Because these named files are real files, the loader cannot infer placeholder-ness from the
filename. Each manifest entry therefore carries **`"placeholder": true`**, and a logo counts as a
placeholder if either that flag is set or it fell back to `placeholder-*.svg`. Delete the flag
when the real artwork lands and the badge disappears on its own.

**Would change it if:** the team sends the real logo pack. Then it is: drop the files in, delete
the `"placeholder": true` flags. No component edits.

## D5 — Fonts

Michroma (400), Space Grotesk (variable 300–700) and JetBrains Mono (variable 400–600), latin
subset only, self-hosted as woff2 in `public/fonts/`. Variable faces were chosen over
per-weight static files: one file each, fewer requests, and the whole set is ~72 KB, which
matters for the "laptop on bad event Wi-Fi" case in the PRD.

## D6 — `base` is configurable, not hard-coded relative

`vite.config.ts` uses `base: process.env.VITE_BASE ?? '/'`. A relative `'./'` base would break the
`/fonts/*` URLs inside `globals.css`. Vercel needs nothing; a GitHub Pages *project* site builds
with `VITE_BASE=/<repo>/`.

## D7 — The engine's types name no DOM types

`docs/03-ARCHITECTURE.md` types `Scene.image` as `{ bitmap: ImageBitmap; … }` and passes assets
carrying `ImageBitmap`s into the renderer. `ImageBitmap` is a DOM lib type, and CLAUDE.md requires
`src/engine/` to be "pure TypeScript with zero DOM/React imports" so it can be unit-tested.

**Decision:** the engine's types describe geometry only.

- `Scene.image` is `{ w, h }` — the layout never needed the pixels, only the aspect.
- The renderer receives drawables through `RenderInput.image` and `RenderInput.rasters`, typed as a
  structural `Drawable` (`{ width, height }`) and a `RasterProvider` callback.
- The canvas context is a structural `Ctx2D` interface listing exactly the methods the engine uses.

The app supplies real `ImageBitmap`s and a real `CanvasRenderingContext2D`, which satisfy these
structurally. The tests supply plain objects. Nothing in `src/engine/` imports the DOM.

**Would change it if:** we ever needed the engine to *create* bitmaps rather than draw them. It
doesn't — rasterisation lives in `src/assets/loader.ts`, on the app side of the line.

---

## D8 — Two shared contracts are hand-written, not generated

`src/engine/types.ts` and `src/engine/metrics.ts` are the two files every other module depends on:
one fixes every signature, the other fixes every geometry constant from Design System § E and § F.
They were written first and are treated as frozen while the rest of the code is built against them.

The practical payoff is that `layout.ts` and `frame.ts` and `render.ts` can be written independently
without negotiating interfaces, and that a magic number can only ever be wrong in one place.

**Rule that follows:** no module outside `metrics.ts` may contain a bare geometry fraction. If you
find yourself typing `0.045`, import `SPONSOR_H` instead.

## D9 — Brand SVGs ship with inline fills, not a `<style>` block

Illustrator exports these marks as a `<defs><style>` block of `.cls-N { fill: … }` rules plus
`class="cls-N"` on every path. **Not every rasteriser applies that CSS.** The headless render check
(`@napi-rs/canvas`, resvg) silently ignored it and drew both brand logos in solid black — cream
artwork rendering as ink on a dark photo, i.e. invisible. It was only caught because the sample
render exists.

Design System § G already asks for "no `<style>` with classes that collide (inline or scoped)", so
the fix follows the spec rather than working around it: at import time the class rules are resolved
and written onto each element as presentation attributes, and the `<style>` block is dropped. The
shipped files contain zero `class=` and zero `<style>`.

**Rule for new assets:** if a sponsor sends an Illustrator SVG with a `<style>` block, flatten it the
same way before committing. A logo that looks right in Chrome can still export black.

## D10 — Placeholder pills are clamped to a 2:1–4:1 aspect band

The first placeholders sized their pill to the name, which made "Aqualink Bangladesh" a 6:1 sliver.
The strip then overflowed and dropped two tier-3 sponsors on every portrait preset — a failure caused
entirely by the stand-in artwork, not by the packing.

Placeholder width is now clamped to a 2:1–4:1 aspect, which is where real sponsor wordmarks actually
live, with the font auto-fitting the clamped box. Mean aspect across the seeded list is 2.73.

With that, all 16 sponsors fit: two balanced rows on every portrait preset, one row on `wide` and
`og`, nothing dropped.

**Caveat worth keeping in mind:** whether the strip drops anything depends on the real logos' widths.
The binding constraint is the Design System's `sponsorH_min` of `0.030·S` (32.4px at 1080), which is
well above the PRD's "≥ 18px" readability floor — so the engine will drop a tier-3 logo rather than
shrink below 32.4px. If the real pack turns out wide and the team would rather keep every sponsor,
the lever is `SPONSOR_H_MIN` in `src/engine/metrics.ts`, not the packing code.

## D11 — SVGs are rasterised through `<img>`, not `createImageBitmap`

`docs/03-ARCHITECTURE.md § Asset loading` prescribes
`createImageBitmap(svgBlob, { resizeHeight })`. **That does not work in Chrome.** It rejects with
`InvalidStateError: The source image could not be decoded` for any `image/svg+xml` blob — verified
in the browser against our own `/brand/mongoltori-light.svg`.

The failure was silent and total: `rasterise()` returned null, so `measure()` fell back to
`aspect: 1`, so every logo was skipped by the renderer and the canvas drew an empty ink rectangle.
Node tests could not have caught it (no `createImageBitmap`), and the headless sample could not
either (`@napi-rs/canvas` decodes SVG fine). It took loading the real page in the real browser.

**Now:** an SVG blob is loaded into an `HTMLImageElement` via an object URL and drawn into a canvas
at the target size, then handed to `createImageBitmap(canvas)`. Before loading, the SVG's own
`width`/`height` attributes are replaced with the target pixel size so the browser rasterises the
*vector* at that scale — an `<img>` holding a viewBox-only SVG otherwise falls back to 300×150 and
the result is soft, which is exactly what the architecture doc warned about.

Raster formats (PNG/WEBP, for sponsors who never ship vector art) still take the
`createImageBitmap(blob, { resizeHeight })` path, which works fine for them.

## D12 — The tone → artwork inversion lives in the loader

Design System § E: a **dark** photo takes the **cream** artwork (`*-light.svg`), a **light** photo
takes the ink one (`*-dark.svg`). `PlacedLogo.tone` carries the *scene* tone, and the layout engine
knows nothing about filenames — by design.

The raster cache was keying straight off the scene tone, so a dark photo got the ink artwork: black
logos on a black background. Visible in the browser as a Mars globe floating with no wordmark, since
the logo's gold and red accents are identical in both variants and only the body tone differed.

The inversion is now a single named function, `artworkFor(tone)`, in `src/assets/loader.ts`, which
is the one place that maps a tone to a file. Anything that needs the rule should call it rather than
re-deriving `tone === 'dark' ? …` inline.

## D13 — Real sponsor artwork, imported as single-tone masters

`img/partners/` holds the team's real logos — 20 of them, which supersedes the
placeholder set and the 16-entry seed manifest. `npm run import:sponsors`
(`scripts/import-sponsors.mjs`) turns them into what the overlay needs and rewrites
`manifest.json`. Re-run it whenever artwork changes.

**Four sponsors were not in the seed manifest**: Logitech, Prolink, K-Silver and
EZ Gadgets. They are parked in tier 3 with arbitrary order. **The team needs to
confirm their tier and ordering.** Also note `blisstyle.svg` is "BLISSTYLE", not the
"Blisstronics" the seed guessed — the slug and name now follow the artwork.

**Why the output is a single-tone raster and not recoloured SVG.** Most of the
supplied logos are near-black (Altium, ODrive, Elgato, Logitech, K-Silver,
CompleTech, and the MSI and Turkish wordmarks). On a dark event photo they vanish,
and the dark-tone scrim darkens the background further — so a per-tone variant is
not optional, and using the colour original for both tones (which Design System § G
allows for single-variant sponsors) would leave half the strip invisible.

Recolouring SVG fills cannot produce a correct variant, because three marks use
white as a **knockout**: the Turkish Airlines bird, the MSI dragon and the SATEL
strapline are white shapes over a coloured shape. Setting those fills to the tone
colour yields a solid blob; setting them to `none` lets the shape beneath show
through. Neither is a hole. Two files are not vector anyway — `mathworks.svg`
embeds a base64 PNG and EZ Gadgets is a palette PNG.

So each logo is rasterised once and its **luminance mapped to alpha**: ink becomes
opaque, near-white falls away over a narrow smoothstep band, giving real knockouts
with clean antialiased edges. Polarity is detected per file from mean ink luminance,
because EZ Gadgets is light artwork whose white wordmark must be kept, not punched.
Masters are emitted cream and ink, cropped to their ink, 512px tall — roughly 6× the
~86px a sponsor is ever drawn at.

Two earlier attempts classified knockouts by whether a white region was *enclosed*;
both failed, because the Turkish bird grazes the edge of its roundel and so reads as
exposed. Luminance is the property that actually distinguishes a knockout from the
ink around it.

**The colour originals are kept** as `<slug>-color.svg|png` next to the variants. If
the team decides a sponsor must appear in brand colour, it is a manifest edit, not a
re-derivation.

**Manifest gained `ext`** (`"svg" | "png"`, default `"svg"`), since these masters are
PNG. `placeholder` is now optional and defaults to `false`.

## D14 — Two shrink floors, because the PRD and the Design System disagree

Design System § E gives the sponsor strip one floor, `sponsorH_min = 0.030·S`
(32.4px at 1080), and drops the lowest tier rather than going below it. The PRD's
acceptance criteria instead require 17 sponsors on `square` to wrap to two rows with
"every logo ≥ 18px tall at 1080px".

With placeholder artwork the conflict was invisible. With the real logos it is not:
20 marks averaging 3.7:1 need about **19.3px** to fit two rows on a square, so the
32.4px floor **dropped seven real sponsors** from every portrait preset — including
tier-1 names, once the cascade started.

**Decision:** keep `SPONSOR_H_MIN = 0.030·S` as the floor for shrinking a *single*
row, exactly as specced, and add `SPONSOR_H_MIN_ROWS = 0.017·S` (18.4px at 1080) as
the floor once the strip has *already wrapped*. The reading is that 0.030 is the
point at which the strip should stop shrinking and wrap instead, while the PRD's 18px
is the real readability limit. All 20 sponsors now fit on every preset, nothing is
dropped, and the PRD criterion holds.

**This is a design decision the team can overrule**, and it is one constant either
way. Reverting `SPONSOR_H_MIN_ROWS` to `0.03` restores the strict floor and the
tier-dropping behaviour with a warning toast.

**Side effect worth seeing before signing off:** at 19px on a square, square-ish
marks (Blisstyle at 0.77:1, EZ Gadgets at 1:1) are physically small next to 6:1
wordmarks, because the layout equalises *height*. That is inherent to 20 sponsors on
a 1080 canvas, not a bug. The lever is curating an "outreach set" — which
`01-PRD.md` already lists as an open question for the team.

## D15 — Phase 3: one export path, and settings-only sharing

**Batch and multi-preset are the same control.** `01-PRD.md` lists them as separate
features (3.2, 3.3), but "every photo × every ticked preset → one ZIP" covers both, and one photo ×
one preset is just the degenerate case. `BatchBar` is therefore a preset checklist plus a format
toggle — there is no "batch mode" to switch into and no second code path to keep in step.

**Everything renders through `renderToBlob`.** The single download, the overlay PNG and the ZIP all
call the same function in `src/lib/render-export.ts`, extracted from `use-export` for the purpose.
CLAUDE.md rule 3 says preview and export must not diverge; three export paths could diverge from
each other just as easily.

**Renders run sequentially, not with `Promise.all`.** Each job allocates a full-resolution canvas —
20 photos × 6 presets at 1920×1080 is 120 of them — and running those concurrently loses the tab.
Same reason the dropzone decodes dropped files one at a time.

**Tone is detected per photo** in batch, as the PRD requires, and `sampleTone` moved to
`src/lib/auto-tone.ts` so the batch reaches the same verdict the preview would. Two implementations
of "is this photo dark?" would eventually disagree.

**The transform resets per job.** A pan framed for the photo on screen means nothing for the next
photo, or for the same photo at a different aspect ratio.

**Share links carry settings, never photos** (`src/lib/share-url.ts`). The payload is base64url —
`+`, `/` and `=` get mangled or truncated when a link is pasted into a chat client. Decoding is
strict: an array, an empty object, or anything without the `p` key returns null rather than silently
resetting the user's settings to defaults. The UI says "never your photo" out loud, because "share"
next to an image editor reads like it uploads the picture.

**The overlay PNG skips the `og` ink mat.** The mat is an opaque border that gives link previews a
crisp edge; in overlay mode — a transparent layer to drop over video in Premiere or CapCut — it would
paint a black frame over the footage. Caught by rendering it, not by reading the code.

**The telemetry label is not prefilled.** `01-PRD.md` says "prefilled with today's date", but a
prefilled field means every framed export carries a date label instead of the specced
`URC · IRC · ERC` default. The date is offered as a placeholder plus a one-click **USE TODAY**
button, so it is one tap away without changing what an untouched export looks like. Flip it if the
team would rather have the date by default.

## D16 — Three tier rows, and logos weighted toward equal optical area

Two changes to the sponsor strip, both requested by the team after seeing the real
artwork on screen. Both override `02-DESIGN-SYSTEM.md § E`.

### Rows are tiers

§ E packs **one or two** rows, split for equal width, and states "Never three rows".
It now draws **one row per tier**, top tier first, capped at three
(`MAX_SPONSOR_ROWS`). Tiers beyond the third fold into the last row rather than
being dropped.

Each tier also gets its own size (`TIER_SCALE` = 1.22 / 1.0 / 0.84). A board that
draws every tier identically does not actually communicate a tier; with 3 platinum,
7 gold and 10 partner logos, the hierarchy now reads at a glance.

The balanced-split logic is gone. It was solving a problem — "which logos share a
row" — that tiers now answer directly.

### Logos are no longer all one height

§ E gives every sponsor height `h2`. That equalises **height**, which is not what the
eye equalises. With the real pack it made MathWorks (6.29:1) and K-Silver (5.44:1)
read as far heavier than Ansys (1.98:1, its box tall because of the "part of
Synopsys" line) or Blisstyle (0.77:1) — the reported symptom was "some of them look
very big and some are small".

Each logo's height is now multiplied by `(3 / aspect) ^ 0.34`, clamped to
0.76–1.62. That is a partial move toward equal **area**: `0` would be the old
equal-height rule, `0.5` full equal-area — which overshoots badly, sending square
marks towering over wordmarks. Measured effect:

| Logo | Aspect | Height × |
|---|---|---|
| Blisstyle | 0.77 | 1.59 |
| EZ Gadgets | 1.00 | 1.45 |
| Ansys | 1.98 | 1.15 |
| SATEL | 2.92 | 1.01 |
| Altium | 4.57 | 0.87 |
| MathWorks | 6.29 | 0.78 |

Two properties worth preserving if this is ever tuned:

- **The reference aspect is a constant (3.0), not the mean of the current
  selection.** Otherwise unticking one sponsor would quietly resize all the others.
- **Width stays linear in the base height** — every logo's width is `h × constant` —
  which is what keeps the shrink search a clean bisection rather than a solve.

Logos within a row are centred on the row's band, since they no longer share a
baseline height.

**Tuning levers**, all in `src/engine/metrics.ts`: `TIER_SCALE` for the hierarchy,
`WEIGHT_EXPONENT` for how hard proportion is equalised, `WEIGHT_MIN` / `WEIGHT_MAX`
for how far one outlier may deviate, `MAX_SPONSOR_ROWS` to go back to two.

**Still imperfect, and probably not fixable automatically:** true optical balance
depends on a logo's cap height and ink density, not just its bounding box. A logo
whose artwork includes a strapline in small type (Ansys, CompleTech, MyActuator)
still reads slightly lighter than a pure wordmark at the same box height. Fixing
that properly means per-sponsor nudges, which is a manifest field the team would
have to maintain.

## D17 — The sponsor banner is an extension, not an overlay

The sponsor strip is no longer drawn on top of the photo. It is a **full-bleed,
opaque, light band across the bottom of the canvas**, and the photo is cover-fitted
into whatever height is left. The output still matches the preset exactly — a
square is still 1080×1080 — so nothing downstream changes.

`Layout` gained `photoH` for the photo region, and `strip.bandHeight` for the band.
The band is measured **first** in `computeLayout`, because everything else has to
fit in what it leaves.

### Consequences, each deliberate

- **Sponsors are drawn in their own brand colours.** That is the whole point of a
  fixed light background: a sponsor's logo can finally appear as the sponsor
  supplied it, instead of the single-tone silhouette D13 needed when the logo sat
  on unpredictable photography.
- **The banner never changes with tone.** `scene.tone` still drives the two TOP
  logos, which do sit on the photo — that behaviour is untouched.
- **The bottom scrim is gone.** It existed to lift sponsor logos off the photo;
  they no longer touch it. `Scrims.bottom` is now nullable.
- **Tone is sampled from the top boxes only**, weighted 0.5/0.5. § E's third
  sampling region was the bottom band, which the banner now covers — letting it
  vote would be sampling the photo in a place no logo is placed.
- **The Mission Frame wraps the photo, not the canvas.** An orange rule ruled
  across a cream sponsor band reads as a mistake. The photo region starts at
  y = 0, so the frame geometry needs no offset.
- **No sponsors selected means no band**, and the photo gets the whole canvas.

### One light-artwork exception

Most sponsor logos are dark-on-transparent and read fine on a light band. EZ
Gadgets is not — its "GADGETS" wordmark is white and would vanish. The importer
measures mean ink luminance and, above 0.62, emits an ink silhouette and flags
`lightArtwork: true` in the manifest so the layout asks for that variant instead.

### Naming convention (the contract for adding a sponsor)

```
img/partners/<slug>.svg         the sponsor's logo IN ITS OWN BRAND COLOURS
img/partners/<slug>.png         ...or PNG, if that is all they sent
```

The filename **is** the slug. `npm run import:sponsors` publishes it as
`public/brand/sponsors/<slug>-color.<ext>` and rewrites the manifest. The twenty
existing files were renamed to match (`Ansys color.svg` → `ansys.svg`,
`Turkish.svg` → `turkish-airlines.svg`, and so on).

**A sponsor with no artwork file is left blank on purpose.** It stays in the
manifest marked `missing: true`, nothing is drawn, and the importer prints it under
"awaiting artwork" — we do not invent or derive a logo. The importer also reports
any file in `img/partners/` that no manifest row claims, which is almost always a
typo'd filename.

## D18 — Tier decides the row, never the size

D16 drew tier 1 larger than tier 3. The team asked for the opposite: **no sponsor
should look bigger than another, whatever its tier.** `TIER_SCALE` is now
`[1, 1, 1]`, so a tier selects only which row a logo lands on.

The optical-area weighting from D16 stays, and is now doing all the work — it is
what makes logos of very different proportions read at the same visual weight.

`TIER_SCALE` is kept as the single lever rather than deleted, so restoring a size
hierarchy is a one-line change.

**Known, and the team is handling it:** Blisstyle's artwork is vertical (0.77:1),
so it still sits awkwardly in a horizontal row. They are supplying revised artwork.

## D19 — Sponsors can be reordered by dragging, within their tier

Each row in the sponsor list is draggable, and dropping one on another moves it
there. The resulting order is what the strip draws.

- **Within a tier only.** A tier IS a row, so a cross-tier drop would silently
  re-rank a sponsor — a commercial decision, not a layout one. The store rejects it
  and the UI will not accept the drop.
- **The order is persisted** (`sponsorOrder` in localStorage). It also travels in a
  share link — though only as of D27; this entry originally claimed it did when the
  payload did not carry it.
- **Keyboard parity.** Dragging is mouse-only, so every row also carries ↑ / ↓
  buttons doing the same move. The PRD requires keyboard operability and a
  drag-only feature would have quietly broken that.
- On boot the saved order is reconciled against the manifest: slugs the user
  arranged keep their positions, and anything new is appended by manifest order, so
  adding a sponsor never scrambles the arrangement.

`Scene.sponsorOrder` carries it into the engine; slugs absent from it fall back to
their manifest `order`.

## D20 — The Mission Frame is now a card

§ F specified a HUD viewport: an orange rule with broken edges, four corner
brackets and two telemetry labels. Against the team's real photography it read as
fussy, and the inset plus the continuous border ate a visible amount of the image.

**The Frame toggle now draws a card.** Photo and sponsor banner share one rounded
container on an ink ground, joined by the orange seam the banner already carries.

What survived from § F, and what did not:

- **Corner brackets stayed.** They are the one Y2K motif the Design System sanctions

- **The continuous border went.** The card's edge is already visible against the

- **The broken edges and HUD openings went.** They only existed to make room for

- **The telemetry labels went**, and the user's note moved to the banner —

## D21 — Sponsor rasters are sized by their ink, not their file

The SVGs looked blurry. Two causes, both fixed:

1. **The optical box was ignored when rasterising.** Sponsor artwork is a
   1080-square with the logo in a thin horizontal slice — CompleTech's ink is 17%
   of its file's height. Rasterising the file at the requested 48px left the actual
   mark 8px tall, and the renderer then stretched it back to 48px. The file is now
   rasterised at `bucket / optical.h`, so the ink lands at the size asked for.
   Capped at 4096px for a pathological file.
2. **The preview asked for export-space sizes.** The preview canvas is scaled by
   `k × devicePixelRatio`, so a logo placed at 30 export px covers ~60 device px on
   a retina screen, but the raster requested was 30px. `useComposition` now wraps
   the provider and multiplies by that factor. The engine still knows nothing about
   the preview scale — the hook does.

## D25 — Chamfered panels, from the reference boards

The team supplied three reference boards (techwear / cyber-industrial poster
design). One vocabulary runs through all three, and it maps onto the existing
palette almost exactly — orange accent, ink ground, cream panels:

- **Barcode strips** and other purely graphic data furniture.
- Dense mono micro-type, numeric codes, registration marks.

## D26 — Uploading a sponsor logo from the app

`.github/workflows/deploy.yml` publishes to GitHub Pages on push to `main`. It
runs the same three gates as local development, in the same order — lint (which
includes the no-pure-white check), test, build — and builds with
`VITE_BASE=/<repo>/` because a project site is served from a sub-path (D6). Pull
requests build and test but do not publish. One-time repo setup: Settings → Pages →
Source = "GitHub Actions". No secrets, because the app is entirely client-side.

### The upload panel

A sponsor logo can now be added in the browser: pick an existing sponsor the
manifest is still waiting on, or add one the manifest does not have at all, and
choose an SVG or PNG. It is measured, placed and exported immediately.

**This is a stopgap, and the panel says so on screen.** The permanent home is still
`img/partners/<slug>.svg` plus a row in the importer (D17). The upload exists for
the case the PRD actually describes — someone at an event, with a logo that arrived
by email an hour ago, and no time for a deploy.

Consequences of `localStorage`, all deliberate:

- **Per-browser.** It does not reach teammates and it does not reach the repo.
- **Budgeted.** 400 KB a file, 2.5 MB total, checked before writing, because data
  URLs run ~33% larger than the file and the editor's own settings share the ~5 MB

- **Lost when site data is cleared.**

- **An uploaded logo counts as a placeholder**, so the header keeps reading

- **Uploading for an existing sponsor takes only the artwork**, keeping the

  quietly re-rank the sponsor.

Adding or removing one re-runs the boot effect rather than mutating the bundle: the
layout needs optical bounds measured before it can place a logo, and re-measuring
through the normal path is simpler than a second code path that mutates in place.

## D27 — Saving the sponsor arrangement, explicitly (superseded by D30)

Dragging already persisted `sponsorOrder` and `sponsorTiers` on a debounce, but the
team asked for a **save button**, and they were right to: an arrangement that is
only auto-saved has no guarantee behind it. Three things could quietly undo it —
`resetDefaults`, a re-registered manifest, or simply not knowing whether it had
been written.

**SUPERSEDED BY D30.** Pinning to `localStorage` made the board follow one browser
on one machine — the team hit exactly that. The save button now writes the manifest
in the repo instead. The reasoning below about *why* an explicit save is needed
still stands; only the destination changed.

**There were two levels.** Dragging took effect immediately, and **SAVE POSITIONS**
pinned the arrangement to its own storage key.

A pinned arrangement is honoured over everything else:

- **`registerSponsors` reapplies it on every boot**, reconciled against the
  manifest — arranged slugs keep their positions, new sponsors append by manifest
  order, and overrides for sponsors that no longer exist are dropped. So adding a
  sponsor never scrambles a saved board.
- **"Reset to defaults" leaves it alone.** That button is about the treatment;
  losing a curated board to it is precisely the surprise the pin prevents. An
  *unpinned* arrangement does go back to manifest order.
- **RESET** next to the save button is the only thing that discards it.

**Share links now carry the arrangement** (`sponsorOrder` and `sponsorTiers` in the
payload). D19 claimed they did; they did not, and this is the fix. Junk tier values
are dropped on decode rather than trusted, the same as the sponsor list.

Verified end to end in the browser: drag, save, reset-to-defaults, reload, discard.

## D28 — A 200 is not proof an asset exists

Swapping BRACU's light-tone artwork to a PNG (D3) meant brand logos had to resolve
`.svg` **then** `.png`. That exposed a latent bug: `fetchBlob` accepted any `ok`
response, and Vite's dev server — like any host with an SPA fallback — answers a
missing path with `index.html` and a **200**. So the deleted `bracu-dark.svg`
"existed", the HTML failed to decode, and the logo silently vanished.

`fetchBlob` now also requires the content type to start with `image/`. Worth
keeping in mind for any future fallback chain: on a static host, probing for a file
by fetching it only works if you check what came back.

## D29 — Phase 4: motion, real-photo QA, and the accessibility pass

### 4.1 Motion

§ D asks for 160ms ease-out on state changes and 400ms on a preset switch, with
`prefers-reduced-motion` honoured. Three gaps were closed:

- **The active glow never animated.** `Pill` used `transition-colors`, and the
  active state's orange ring is a `box-shadow` — so it snapped in. The transition
  now names `box-shadow` explicitly.
- **`ease-out` was missing** on the sponsor-row and thumbnail transitions.
- **The 400ms preset switch did not exist.** The canvas's CSS box now eases over
  `--mt-preset-ms`, but **only while a switch is in flight** — applied via a
  `data-resizing` attribute for the duration. A standing transition would also
  catch a window resize, which fires continuously as the user drags the window and
  would visibly lag.

**Not done, deliberately:** overlay geometry does not interpolate between the two
layouts. § D's "overlays glide" would mean lerping every placed rect across the
switch. It is possible — `renderComposition` would still be the only draw path —
but it doubles the layout surface for a 400ms effect nobody exports, and a
half-interpolated frame is not a composition anyone would want.

### 4.2 Visual QA on real photos

`npm run sample -- --photo <path>` renders any real photo through the actual
pipeline, **including auto tone detection**, so QA reflects what the team would
see rather than a tone nobody would pick.

Checked against five real photos from `img/`. Auto-tone discriminated correctly
every time: the bright Mars-Desert team photo → **light**, the indoor EMK seminar,
the outreach sessions and the rover shots → **dark**.

- **Tone threshold 0.52 stands.** No misclassification to correct.
- **Scrim default 0.7 stands.** On the indoor seminar the top of the frame is
  already dark, so the scrim is invisible and harmless; it earns its keep on a
  dark-tone photo with a bright ceiling. Nothing in the sample set argued for a
  different default.
- **Fixed a bug in the QA script itself**, not the app: it picked the artwork
  variant from the CLI flag *before* auto-tone ran, so a light-tone render drew the
  cream BRACU logo — nearly invisible on a bright sky. It now loads both variants
  and lets the raster provider choose. Verified separately in the browser that the
  app had always resolved the right one (cream `rgb(244,243,238)` for dark tone,
  official navy `rgb(41,51,95)` for light).

### 4.3 Accessibility and performance

**Lighthouse itself was not run** — no Chrome binary is reachable from the CLI in
this environment, and reporting a score I did not measure would be worthless. The
substance was audited instead, against the **production build**:

**axe-core 4.10: 0 violations, 44 passes.** It found two real problems first:

- **`color-contrast`, serious, 17 nodes.** `--mt-text-mute` at § B's
  `rgba(244,243,238,0.38)` measures **3.34:1** on every surface in the app — under
  WCAG AA's 4.5:1 for small text. 0.48 is the minimum that clears it; the token is
  now **0.50**. This deviates from § B, which chose the value by eye rather than by
  measurement.
- **`label`, critical.** Both `sr-only` file inputs — the photo dropzone and the
  sponsor upload — had no accessible name. Both now carry an `aria-label`.

**Measured performance** on the production build: FCP 260ms, load complete 122ms,
36 requests, ~1.0 MB transferred. Of that, `dist/brand` is 1.4 MB on disk against
396 KB of JS/CSS and 76 KB of fonts — **the sponsor artwork is the payload**. It is
precached by the service worker, so the PRD's "laptop on bad event Wi-Fi" pays it
once; but it is the thing to look at first if that ever becomes a complaint.

**One trap worth recording:** the service worker served the *previous* build on
first load, so the first two axe runs scored the old CSS and looked like the fix
had failed (`transferKB: 1` was the giveaway). Unregister the worker and clear
caches before auditing a fresh build.

## D30 — The sponsor board lives in the manifest, not the browser

D27 saved the arrangement to `localStorage`. That was the wrong store: the team
arranged the board on one machine, opened the app on another, and got the manifest
order back. An arrangement is not a per-user preference like a zoom level — it is a
decision about how the team's sponsors are presented, and it belongs in the repo
with everything else that decides that.

**`public/brand/sponsors/manifest.json` is now the only store of record.** Its
`tier` and `order` fields already described the board; saving simply rewrites them.

### How saving lands

- **`npm run dev`** — the app POSTs to `/__manifest`, a dev-only Vite middleware
  (`manifestWriter()` in `vite.config.ts`) that writes the file on disk. It shows up
  in `git status`; commit it and every teammate and every browser gets that board.
- **The deployed site** — static, with nowhere to write, so the app downloads
  `manifest.json` and the toast says where to put it.

The endpoint is `apply: 'serve'` so it never exists in a build, writes one fixed
path so nothing can be redirected, caps the body at 256 KB, and parses and
shape-checks the JSON before touching the file — a malformed request must not
truncate the manifest. Verified: `GET` → 405, malformed body → 400, wrong shape →
400, valid write → file changed and `git status` shows it modified.

**A 200 is not proof the write happened** — the same trap as D28. A static host
with an SPA fallback answers any path with `index.html` and a 200, which would make
the app claim it had saved. `saveManifest` requires the dev plugin's own JSON
acknowledgement before reporting success; anything else falls through to the
download.

### What changed in the app

- **No arrangement in `localStorage` at all.** The key is gone, and `sponsorOrder`
  and `sponsorTiers` were removed from the persisted settings. Every boot reads the
  board off the manifest.
- **`arrangementDirty` replaces `arrangementPinned`.** The panel reads
  `◆ MATCHES manifest.json` or `↳ UNSAVED — SAVE TO WRITE manifest.json`, and
  **REVERT** discards unsaved dragging. Save is disabled when there is nothing to
  save.
- **Unsaved dragging survives an asset reload.** `registerSponsors` also runs when
  the bundle reloads mid-session — uploading a sponsor logo does that — so it now
  keeps a dirty board and reconciles it against the new manifest rather than
  discarding work because someone added a logo.
- **`applyArrangement` renumbers `order` from 1 within each tier**, so the file
  stays readable by hand and a hand edit and an app edit produce the same shape.
  Unit-tested, including the round trip: save an arrangement, reload it, get the
  same board.

**Trade-off, stated plainly:** on the deployed site a drag is now lost on reload
unless it is saved and committed. That is the intended behaviour — the alternative
is the hidden per-browser state that caused the problem.

### A bug the browser test caught

Clearing the dirty flag after a successful write by calling `revertArrangement()`
reset the order from `registrySlugs()` — which still held the **pre-save**
in-memory order. The file on disk was correct, but the list snapped back to the old
board and stayed wrong until a reload: the UI contradicting the file it had just
written.

`commitArrangement()` replaces it. The store's sponsor registry holds the same
objects the asset bundle exposes as `meta`, so writing the new `tier`/`order` onto
them brings the list, the layout and the file into agreement without a reload.

**Verified end to end in the browser**, on the dev server: clean state reads
`◆ MATCHES manifest.json` with save disabled; a nudge flips it to
`↳ UNSAVED` and enables save and REVERT; saving toasts
`SAVED TO manifest.json — COMMIT IT`, the order holds, and `git status` shows the
file modified with the new order. Then — the actual thing the team asked for —
**every browser store was wiped (localStorage, sessionStorage, caches, service
worker) and the board still came back from the file.** The only key left is
`mt-brandkit:v1`, holding preset, tone, frame, scrim, selection and label; nothing
about the arrangement.

## D31 — Mobile was broken in four ways, all found by looking

Tested at 390px by rendering the app inside a narrow iframe — the OS window
resize did not change the page's viewport, so the media queries never fired and
the "mobile" screenshot was just the desktop layout at a smaller scale. The iframe
gives the page inside it a real 390px viewport.

**1. The side panels collapsed and their content overlapped.** Both carried
`min-h-0`, which is what lets the desktop GRID columns scroll. In the stacked
mobile column the same rule let them shrink far below their content — the left rail
was 75px tall holding six preset pills — so FORMAT rendered on top of TREATMENT.
`min-h-0` is now `lg:` only, with `shrink-0` below it.

**2. Two nested scrollbars.** The shell had a fixed height and its own
`overflow-y-auto` at every width, so the page scrolled AND an inner div scrolled.
There are now two deliberate models: desktop pins the shell to the viewport so the
preview never leaves the screen and each column scrolls on its own; **mobile lets
the page scroll and nothing inside it**, because an inner scroller on a phone
fights the browser's own chrome-collapsing scroll. `html, body { overflow: hidden }`
is scoped to `lg` for the same reason — locking it on a phone would make everything
below the preview unreachable.

**3. Sponsors could not be reordered on a phone at all.** HTML5 drag-and-drop does
not work on touch, and the ↑/↓ buttons were `opacity-0` until hover — which never
happens on a touchscreen. The arrows are now always visible below `lg` and keep
the reveal-on-hover on desktop, where dragging is the primary gesture. The `⠿`
drag handle is hidden below `lg`, since advertising a gesture that cannot work
there is worse than not showing it.

Verified after the fix at 390px: no overlap, no horizontal overflow, nothing wider
than the viewport, a single page scroll, and tapping ↑/↓ reorders and marks the
board unsaved. Desktop re-checked: three columns, column-level scrolling, arrows
still hover-revealed.

Also fixed in passing: the telemetry field still read `DEFAULT: URC · IRC · ERC`,
which stopped being true at D23 when the standing text was removed.

**4. The photo dropzone advertised a gesture phones do not have.** The empty state
read `› DROP IMAGE OR CLICK` inside a dashed drop panel, with `— or paste` under
it. Tapping it already opened the file picker, so only the affordance was wrong —
but an affordance that names an impossible gesture reads as a broken control.
Below `lg` the panel is now an ordinary upload button: a solid border, an orange
`⬆ UPLOAD PHOTO` pill and the format list without the paste hint. From `lg` up it
is the dashed drop panel it always was. One button, one file input, two faces —
no device sniffing, just a breakpoint. Verified at 390px: tapping fires the file
input's own click, and the target is 344×128 CSS px.

## D32 — The sponsor manifest is never cached, by anything

The board would revert on refresh even though SAVE POSITIONS had written
`manifest.json` to disk. The write was fine; the *read* was not.

`manifest.json` was in the service worker's **precache** — `globPatterns` swept
`json`, and `includeAssets: ['brand/**/*']` swept it a second time. Precaching is
right for artwork, which only changes when the build does, and wrong for the board,
which is the one file in `public/` the app rewrites at runtime. The effect is
nasty because it is not scoped to production: any origin that has ever served a
build keeps that service worker, so `localhost:5173` under `npm run dev` would
answer from a precache belonging to a build made days earlier. The dev server
wrote the file, the page reloaded, and the worker handed back the old board — with
nothing in the UI to suggest a stale read.

Now: `globIgnores` keeps it out of the precache, `includeAssets` is narrowed to
`brand/**/*.{svg,png}` so it cannot slip back in behind that, and a NetworkFirst
runtime route keeps the offline story intact — network wins whenever it is
reachable, the cached copy is only the fallback. `loadManifest` also fetches with
`cache: 'no-store'`, which closes the same hole in the plain HTTP cache.

Verified against a real build with a live worker: edit the served `manifest.json`,
refresh, board follows. Before the fix the same test kept showing the old order.

**This is also the answer to "does save actually work?" — yes, and it always did.**
On `npm run dev` it writes `public/brand/sponsors/manifest.json` and the status
line reads `SAVED TO manifest.json — COMMIT IT`. On the deployed site there is
nowhere to write, so the file **downloads** and the line reads `manifest.json
DOWNLOADED — REPLACE public/brand/sponsors/manifest.json`; refreshing there reverts
by design, because the copy in the repo has not changed yet. The two cases are
told apart by the status line, not by the button.

## D33 — Vercel, and one endpoint so saving stops being a download

On a static host SAVE POSITIONS had nowhere to write, so it downloaded
`manifest.json` and asked someone to drop the file into the repo by hand. That is
a fine fallback and a bad default: the arrangement is finished in the app and then
has to survive a file manager, a commit and a push before anyone else sees it.

GitHub Pages cannot do better — it serves files and nothing else. Vercel can run a
function, so the site is now deployed there and SAVE POSITIONS POSTs to
`api/manifest.ts`, which commits `public/brand/sponsors/manifest.json` through the
GitHub API. The repo stays the single source of truth (D30); the function stores
nothing and reads nothing back. A save is a commit, and the redeploy that follows
is how everyone else gets the new board.

**The endpoint is the same URL in both worlds.** The client posts to `/__manifest`;
in development that is the Vite middleware writing to disk, in production
`vercel.json` rewrites it to `/api/manifest`. One code path, one guard, no
environment sniffing in the client — it tells the two apart only by whether the
acknowledgement carries a commit sha.

**A public write endpoint needs a guard**, or the first person to find
`/api/manifest` owns the sponsor board. `MT_SAVE_KEY` is a shared secret compared
in constant time; the app keeps it in `localStorage` and sends it as a header.
That is a deliberate exception to "nothing about the board lives in the browser" —
the key is permission to write the board, not the board. A wrong key returns 401
and the app says so instead of quietly downloading, because silently falling back
would teach people to ignore the one signal that matters.

The body is checked before anything is committed: it must parse, it must have a
non-empty `sponsors` array, and every entry must have `slug`, `tier` and `order`.
The path is a constant, never taken from the request. GitHub's `sha` precondition
handles two people saving at once — the second gets a 409 and is told to reload
rather than clobbering the first.

**What went away.** `.github/workflows/deploy.yml` — Vercel deploys now. What
replaced it is `ci.yml`, which still runs lint, tests and the build on every push
and PR, because Vercel runs only the build and would happily ship a red test suite.
`VITE_BASE` stays in `vite.config.ts`: Vercel serves from `/`, but a subpath host
still needs it, and it costs one line.

Trade-offs taken knowingly: the board is live for everyone about a minute after a
save rather than instantly, since it arrives by redeploy; a save needs GitHub to be
up; and the project now has a backend, which `CLAUDE.md` previously ruled out. It
is one function, one file, no state, and no photo ever reaches it — those never
leave the browser.

## D34 — A saved board reverting on every reload was never the file

Reported as "every reload it changes to default, even though manifest.json in
GitHub is the updated one". It was not: the file was right in the repo, right on
disk, and right in the response the server sent. What was wrong was what the
browser chose to hand the app instead.

D32 took `manifest.json` out of the precache and added `cache: 'no-store'`. Both
were necessary; neither was sufficient, for two reasons that only show up on a
machine with history.

**A service worker ignores `no-store`.** `no-store` instructs the HTTP cache. A
worker's fetch handler sits in front of that and answers from its own Cache
Storage regardless of what the request asked for. So a worker installed by an
*older* build — one whose precache still contained the board — keeps serving that
board, and no amount of rewriting the file or redeploying changes what the page
sees. The fix is to ask for a URL no precache has an entry for: the manifest is
now fetched with a `?v=<timestamp>` query. Workbox matches precache entries by
exact URL (bar `utm_`/`fbclid`), so the query misses every entry and falls through
to the network — including on workers already installed on people's machines,
which is the point. Verified in a real build: a fabricated precache entry matches
the bare URL and does not match the query-bearing one.

**Dev never gets a replacement worker.** Serve a production build once from
`localhost:5173` — a `vite preview` on that port, `npx serve dist`, anything — and
that worker stays registered for that origin. `npm run dev` ships no service
worker, so nothing ever supersedes it, and every subsequent dev session is served
someone's week-old precache with no sign on screen. `src/main.tsx` now unregisters
any worker it finds in a dev build and deletes its caches, warning once in the
console. Verified by installing a stand-in worker on the dev origin: one reload
and it is gone, caches with it.

**And the update itself was a reload behind.** The auto-injected registration
installs a new build and leaves it for the next time the tab is opened from
scratch, so the first load after a deploy renders the *previous* build — the
mechanism behind "I deployed and nothing changed". `registerSW({ immediate: true })`
in `src/main.tsx` (with `injectRegister: null`, so there is exactly one
registration) takes control and reloads once. Verified: before, a new build needed
two reloads; after, one.

The lesson worth keeping: **a file being correct in git, on disk and in the HTTP
response is not evidence the app read it.** Between the response and the app sit
an HTTP cache and a service worker, and only one of those two honours cache
headers.

## D35 — The function signature, and why the live site kept showing the old board

Two faults, found by pointing curl at the deployed site instead of reasoning about
it. Worth recording together, because each one alone looked like the other.

**The endpoint was crashing.** `GET /api/manifest` returned
`FUNCTION_INVOCATION_FAILED`, a 500. It was written with named `GET`/`POST`
exports taking a `Request` and returning a `Response` — which is the **Next.js App
Router** convention, not Vercel's. A plain file in `api/` is invoked the Node way,
`(req, res)`, and exporting the wrong shape is not a build error: it type-checks,
it deploys, and it fails at the first request. It is now `export default async
function handler(req, res)`, with the small slice of Node's req/res it uses typed
locally so the file still needs no dependency. `readBody` normalises all four
things the platform may hand over — parsed object, string, Buffer, or an unread
stream — because which one you get depends on the content type.

**The site was serving an old deployment.** The board in the repo said
`myactuator, satel, msi, sbg-systems`; the site served `completech, msi,
turkish-airlines` — and kept doing so after a redeploy, which is what made it look
like caching. It was not. The live bundle contained the SAVE KEY field, so the
deployment was built from the commit that added it, and the two later commits —
the ones that changed `manifest.json` — had never been built. **Vercel's
"Redeploy" rebuilds the commit that deployment was made from, not the newest
one**, so pressing it repeatedly rebuilds the same stale source for ever. A push,
or "Deploy" from the latest commit, is what moves it.

The diagnostic that settled it, and the one to reach for next time: fetch the
deployed asset itself. `curl https://<site>/sw.js` says which build is live,
`curl https://<site>/brand/sponsors/manifest.json` says what the server actually
returns, and comparing that with `git show origin/main:<file>` says whether the
deployment is even from the commit you think it is. Three commands, no theories.
